## 🔬 原因分析

### 問題1: 名前・診察券番号が未入力

**原因**: スタッフが管理画面で編集していない

**理由**:
- ユーザー登録直後は`real_name`と`ticket_number`は空
- スタッフが患者一覧から「編集」ボタンを押して入力する必要がある
- 恐らく、スタンプ付与のトラブル対応に追われて、入力を忘れた可能性

**対策**: 運用フローの見直し

---

### 問題2: スタンプの三重付与

#### 原因①: 二重送信（Double Submit）

**2回目と3回目のスキャンが0.089秒差**

考えられるシナリオ:
1. ユーザーがQRコードをスキャン
2. LIFFアプリがAPI呼び出し
3. **ネットワーク遅延でレスポンスが遅い**
4. ユーザーが「エラーかな？」と思って**もう一度ボタンをタップ**
5. **ほぼ同時に2つのリクエストが送信される**

#### 原因②: LIFFアプリ側の多重送信防止が不十分

**現状の実装:**
- QRコード読み取り後、ボタン連打を防ぐ仕組みが不十分
- リクエスト送信中のローディング表示が不明確

---

### 問題3: データベース不整合

#### なぜstamp_historyに2回目・3回目が記録されていないのか？

**可能性①: トランザクションの部分的ロールバック**
- event_logsへの書き込みは成功
- stamp_historyへの書き込みは失敗
- しかしprofiles.stamp_countは更新された

**可能性②: RLSポリシーの問題**
- event_logsには書き込み権限がある
- stamp_historyには書き込み権限がない（何らかの条件で）

**可能性③: 非同期処理の失敗**
- event_logs記録 → 成功
- profiles.stamp_count更新 → 成功
- stamp_history書き込み → **失敗**

#### 🔴 優先度: 高

**1. QRスキャンAPIの二重送信防止（LIFFアプリ側）**

**場所**: LIFFアプリのQRスキャン処理
**対策**:
```typescript
// ボタン無効化
const [isProcessing, setIsProcessing] = useState(false);

const handleQRScan = async (qrData) => {
  if (isProcessing) return; // 処理中は何もしない

  setIsProcessing(true);
  try {
    const result = await fetch('/api/stamps', { ... });
    // 成功メッセージを明確に表示

  }
```

```typescript
// 同一ユーザー・同一QRコードの短時間内重複チェック

  .eq('user_id', userId)

if (recentStamp) {

  );
```

## 📌 結論

### 問題の本質

1. **名前・診察券番号未入力**: 運用フローの問題（スタッフが入力を忘れた）
2. **スタンプ三重付与**:
   - LIFFアプリ側の二重送信防止が不十分
   - ネットワーク遅延時のユーザー行動（「エラーかな？」と思って再スキャン）
3. **データベース不整合**: トランザクション管理の問題

### 今回のケースの特徴

- **初めての報告事例ではない可能性**
  - データベース不整合があることから、過去にも同様の事象が発生していた可能性
  - ただし、ユーザーが気づかなかった、またはスタッフが静かに修正していた

### 緊急性

- **即座の対応は不要**（スタッフが既に修正済み）
- ただし、**再発防止のため技術的対応は必要**
