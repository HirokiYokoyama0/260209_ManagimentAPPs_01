## 0. 要旨

マイルストーン特典（歯ブラシ等）が同一マイルストーンで `reward_exchanges` 2行（`available`＋`completed/pending`）に重複し、**1到達で特典を2回受け取れる**状態が実患者407人・446件に発生していた。**新規発生の停止(B)→既存の掃除(C)→構造的な施錠(D-fix)** を、患者の交換を一度も止めずに完了した。

---

## 1. 根本原因

- LIFFの `/api/rewards/exchange` が、既存の `available`（自動付与）を**更新せず**別レコードをINSERTしていた（`pending` のみチェックし `available` を見ていなかった）。
- 真因：`reward_exchanges` は **026ハードニングで anon UPDATE が塞がれており**（`reward_exchanges_deny_update` = permissive `USING(false)`）、LIFF(anon・doc107でservice role不可)のUPDATEが0行→INSERTフォールバックしていた。
- 加えて **`UNIQUE(user_id,reward_id,milestone_reached)` が本番未適用**（スキーマ文書05のフル制約記載は誤り・実DB未適用）。
- 重複の必要十分条件：**「自動付与availableが事前に存在」×「exchangeで別レコード作成」**（横山123459: ms30=重複／ms100=重複なしで実証）。ポイント数(15/10)・患者属性は無関係（検証済み）。

---

## 2. 対応（B → C → D-fix・順序厳守）

### B｜新規重複を止める（2026-07-19）
- **LIFF**: `/api/rewards/exchange` を update-not-insert（available→pendingをアトミックUPDATE／無ければINSERT／fail-open）。`grantMilestoneReward` に存在チェック＋23505キャッチ。
- **RLS**: `supabase/033_allow_anon_update_reward_exchanges_available_to_pending.sql` を本番適用（2026-07-19 14:50 UTC）。anonに **available→pending 遷移のみ**許可。
  - 🔴 **033 は絶対にDROPしない**（消すとanon UPDATE不可に戻り重複再発）。026系RLSを再実行/再作成する時も033を必ず残す。
- **ダッシュボード**（commit b8acd8c）: `grantMilestoneReward`([116])に存在チェック、`/api/reward-exchanges/[id]/complete` に兄弟available/pendingのcancel（fail-open・二重蛇口）。
- 検証: 6日間の実トラフィックで新規重複0。

### C｜既存backlogのクリーンアップ（2026-07-26）
- `scripts/cleanup-reward-duplicates-exec.ts --execute`（論理削除・実行時再計算・楽観ガード・冪等）。
- 493タプル/495行を `cancelled` 化（内訳: available488 / pending1 / completed6）。
- KEEPルール（オーナー方針）: completed>pending>available を残す。**completed×2は遅い方を残す／completed+pendingはpendingをcancel**。
- 事前バックアップ: Supabaseで `reward_exchanges_backup_20260726`（テーブル複製）＋スクリプトが対象495行のJSONバックアップ生成。
- 実行後ゲート: **有効重複タプル=0** 確認。

### D-fix｜施錠（2026-08-01）
- `supabase/034_add_partial_unique_reward_active.sql` を本番適用。
  ```sql
  CREATE UNIQUE INDEX uq_reward_active
    ON reward_exchanges (user_id, reward_id, milestone_reached)
    WHERE status IN ('available','pending','completed');
  ```
- **部分ユニーク**（cancelled/expired除外）＝Cの論理削除と両立。フルUNIQUEは cancelled+completed が同一タプルに残り作成失敗するため不可。
- `is_valid=true / is_ready=true` 確認済み。以降、同一マイルストーンへの重複有効行INSERTは `23505` で拒否＝**構造的に再発不能**。

## 4. 恒久的な注意事項（後任・監査向け）

1. **`reward_exchanges_anon_claim_available`（033）は DROP 厳禁**。消すと重複再発。RLS再作成時も残すこと。
2. **一意制約は部分ユニーク `uq_reward_active`**（`WHERE status IN ('available','pending','completed')`）。フルUNIQUEにしないこと（論理削除と両立しないため）。
3. **述語 `available/pending/completed` を三者（LIFF exchange／DB制約／ダッシュボードdedup）で一致**させること。ズレると片側で漏れる。
4. **ドキュメント番号・マイグレーションはrepo毎に独立**（`Doc_dashboard/` と LIFFの `Doc_miniApps/` 等）。同番号でも別物。連携文書のリンクや `../app/...` は開くrepoで解決先が変わる。
5. スキーマ文書 [05](05_Database_Schema.md) は §reward_exchanges 制約を部分ユニークに訂正済み（旧フルUNIQUE記載は誤り）。

## 5. 別タスク（未対応・doc106関連）

同じ anon UPDATE不可により、LIFF側の以下が静かに失敗の疑い（**本件とは別・患者影響は小**）：
- `invalidateMilestoneRewards`（スタンプ減少時 →cancelled）
- 期限切れ自動更新（pending→expired）

推奨: **anon権限を広げない**（他人の特典をcancel/失効できてしまう）。期限切れは「読み取り時判定 or スケジュール実行」、invalidateは service role 側に寄せる。ダッシュボードの invalidateMilestoneRewards は元々 service role で稼働（影響なし）。
